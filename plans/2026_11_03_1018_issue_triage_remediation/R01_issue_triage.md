### 2.2 T-02（BR 問題二）的修復方案比較

### 問題現況
- Linux 上的探測函式永遠回答「可以背景常駐」，所以 CLI 每次都會偷偷 spawn 一個 daemon 行程，而且不等它就緒。
- 在 agent 容器裡，這個行程會在單次命令結束時被一起回收，所以每次都白跑一趟，熱派發永遠不會生效。
- 使用者和 agent 都看不到任何提示；`skill` 文件承諾的 [BLOCKER] 指引也從來不會出現。
- 手動執行 `server start -d` 時，就算 readiness 逾時，結束碼仍是 0，agent 會誤以為已經啟動成功。

| 方案 | 做法 | Linux 桌機 | Windows | Agent 容器沙盒 | 主要風險 |
|---|---|---|---|---|---|
| **A 執行期偵測** | spawn 之後輪詢 daemon 狀態；啟動失敗就印 [BLOCKER]，指令本身照常以冷派發完成 | 不變（每個 session 第一次 spawn 時多約 0.3-3 秒輪詢） | 不變 | **只能抓到「啟動當下就失敗」**；「當次啟動成功、命令結束後才被回收」的情況抓不到，所以每次仍會白白 spawn | 增加延遲；有一部分情況漏抓 |
| **B 環境特徵偵測** | 偵測容器特徵（`/.dockerenv`、cgroup、特定環境變數），命中就直接回答「不可常駐」 | 不變 | 不變 | 命中時直接印 [BLOCKER]、不 spawn，零成本 | **誤判**：devcontainer、Codespaces 這類可以正常常駐的容器會被誤判成不可常駐，熱派發因此失效；**漏判**：沒有這些特徵的沙盒抓不到；特徵清單需要長期維護 |
| **C 兩者並用** | 先用 B 擋掉已知沙盒，A 處理其餘情況 | 同上 | 同上 | 覆蓋面最大 | 同時有 B 的誤判風險和 A 的延遲；程式碼最多 |

**所有方案都要一起做的部分**：`server/scripts/cli.py` readiness 逾時且確認進程已不存在時，改回傳 1（約 3 行，修正後 agent 能正確判斷失敗）。

**另外需要你決定**：
1. 啟動失敗時，**原本的指令要不要也回傳非零結束碼**？目前的 [BLOCKER] 文案寫的是「以本地冷派發臨時兜底」，所以我建議只印提示、結束碼不變；改成非零是破壞性變更。
2. 如果採用 B，是否同時提供 `YSCB_FORCE_DAEMON=1` 這類強制開關，讓被誤判的容器可以關掉偵測？
3. `require_server_for_agents`（T-21）要補上實作，還是從文件中刪除？

### 2.3 T-13（BR 問題三與 Y-15）的修復方案比較

### 問題現況
- 停止 server 時，程式先解鎖，再刪除 `daemon.lock` 檔。
- 解鎖和刪檔之間有一段空窗。如果這時有兩個新行程同時啟動：
  1. 行程 B 開到即將被刪的舊檔，取得鎖。
  2. 舊檔隨即被刪除。
  3. 行程 C 建立一個新檔，也取得鎖。
  4. 結果兩個 master 同時在跑。
- 在 virtiofs 上，「刪除」和「建立」之間的快取不同步，可能讓 `os.open` 回傳 EEXIST，但這點還沒有實機重現。
- 而 `lock.py:54` 沒有處理這個錯誤，會直接崩潰。

| 方案 | 做法 | 能解決 EEXIST 崩潰 | 能解決兩個 master 並存 | 副作用 | LOC |
|---|---|:-:|:-:|---|:-:|
| **A 保留鎖檔加重試** | `_cleanup_state` 不再刪除 `daemon.lock`，只刪 state 檔；`lock.py` 遇到 EEXIST 時有限次重試（例如 3 次、間隔 50ms），其他錯誤照常拋出 | ✅ | ✅ 從根本消失：路徑永遠指向同一個檔案 | `.cache/server/daemon.lock` 會一直存在（0 byte）。**已查證沒有任何程式碼把「檔案存在」當成「daemon 在執行」**，判斷依據一律是能否取得鎖；log 清理本來就把它列為受保護檔案 | 程式約 15、測試約 35 |
| **B 只加重試** | 只改 `lock.py` | ✅ | ❌ 刪檔造成的競態仍然存在 | 無 | 程式約 8、測試約 20 |

**選配加強**（兩個方案都可加，約 10 行）：取得鎖之後，比對已開啟的檔案和目前路徑上的檔案是不是同一個（inode），不一致就重試。可以防範未來又有人加回刪除動作。
