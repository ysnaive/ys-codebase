# AI Agent 技能結構、雙軌觸發契約與漸進式揭露設計標準 (Skill Design Standards)

本文件定義 AI Agent 技能的通用結構、YAML Frontmatter 雙軌結構化 `description` 觸發契約、四元素目錄拓撲、漸進式揭露（Progressive Disclosure）上下文經濟、條件式工作流護欄與三層縱深安全設計標準。

---

## 1. [!] YAML Frontmatter 與雙軌結構化 `description` 契約 (Dual-Track Trigger Contract)

`SKILL.md` 頂部 YAML Frontmatter 會在 Agent 啟動時常駐預載入系統提示詞（System Prompt），作為宿主進行技能探索與意圖匹配的**首要預載路由信號（Primary Preloaded Routing Signal）**（與宿主命令路由、全專案條件路由表及對話上下文協同運作）：

1. **檔名與元資料解析防護（Metadata Hygiene）**：
   - **主檔名大小寫**：入口檔名必須精確為 `SKILL.md`（嚴禁 `skill.md` 或 `SKILL.MD`），且技能目錄內**禁止放置給人類閱讀的 `README.md`**（避免雙重說明檔混淆 Agent 檢索）。
   - **`name` 格式限制**：長度 1~64 字元，僅允許小寫英文字母（`a-z`）、數字（`0-9`）與單一連字號（`-`），禁止連字號開頭/結尾或連續連字號（`--`），且必須與父資料夾名稱完全一致。
   - **YAML 保留字元與標籤防護**：`description` 總長須低於 1,024 字元，**嚴禁包含 `<` 或 `>` 角括號**（防止破壞 System Prompt 之 XML/HTML 封裝結構）；若以 `[`、`{`、`*`、`!`、`>`、`|`、`&`、`%`、`@` 等 YAML 保留字元開頭，必須以雙引號 `"..."` 包裹。
2. **高密度、自包含與雙軌結構化邊界（Dual-Track Structured Boundaries — A1 + B2）**：
   - **關鍵識別詞前置與自包含 I/O**：`description` 應將核心動詞與領域名詞置於前段（防範宿主預載長度截斷），並具體陳述**「輸入標的、處理動作與輸出交付物」**（嚴禁依賴「依循某某內部規範」等外部未知脈絡）。
   - **雙軌分流契約**：依技能觸發性質嚴格分流為「軌跡 A（被動環境攔截型）」與「軌跡 B（主動斜線指令型，細分 B-Strict 與 B-Assist 兩級）」：

| 技能類型與分級 | 適用場景 | 強制 `description` 結構公式與防搶路由守則 |
| :--- | :--- | :--- |
| **軌跡 A：被動／環境攔截型技能**<br>*(Ambient / Intent-Driven Skills — A1 正向邊界契約)* | 仰賴自然語言業務意圖、特定檔案路徑或原生工具調用前自動攔截觸發（如開發 SOP、測試規範、文檔規範、CLI 守門、代碼檢索） | **兩段式正向邊界（＋選配無點名負向邊界）**：<br>`{核心用途、處理對象與交付物}。觸發情境：{具體動詞、目標檔案路徑特徵與前置攔截時機}。`<br>1. **預設不寫 `排除情境：`（根除粉紅大象效應與網狀耦合）**：優先以高特異性動詞與明確產物路徑（如 `plans/` vs. `docs/` vs. `tests/`）從正向自然切開領域。<br>2. **選配同源負向邊界（嚴禁跨技能點名）**：唯獨在同領域兩個技能極易混淆時，始可選配補充 `排除情境：{不處理之動作或產物類型}。`，但**嚴禁在 `description` 中點名其他技能名稱（禁止寫 `(改用 xxx)`）**，跨技能轉交邏輯一律下沉至 `SKILL.md` 內文。 |
| **軌跡 B-Strict：重型／授權斜線指令型技能**<br>*(Strict Command-Locked Skills)* | 具高 Token 消耗、大批次重構、修改源碼或版本發布副作用，**絕不允許在一般技術討論中由模型自行猜測觸發**（如專項重構、批次自動化推進、版本晉升發布） | **純斜線鎖定契約（關閉自然語言後門）**：<br>`{1 句話核心目的與交付物}。僅於顯式輸入 /{cmd} 時觸發，嚴禁主動觸發。`<br>*(徹底拔除「或明確指示...」自然語言後門，防止開發者討論「如何優化」時誤啟動重型工作流)* |
| **軌跡 B-Assist：會話控制／輔助斜線指令型技能**<br>*(Assisted Command / Session Skills)* | 屬會話狀態切換、斷點接續、上下文初始化、互動教學或引導建置，允許開發者以顯式斜線或明確委託語句啟動（如進度接續、暫停交接、互動教學引導） | **斜線＋明確委託雙通契約**：<br>`{1 句話核心目的與交付物}。僅於顯式輸入 /{cmd} 或明確要求{具體委託動作}時觸發。`<br>*(嚴禁包含 `(或 /Cmd)` 大小寫變體或內部步驟細節；`{具體委託動作}` 須為完整委託動詞片語而非單一泛用詞)* |

## 2. 四元素標準目錄拓撲與漸進式揭露法則 (Directory Topology & Progressive Disclosure)

1. **四元素標準技能目錄拓撲（4-Element Skill Topology）**：
   - **`SKILL.md`（必選，核心工作流與決策樹）**：嚴格控制在 **500 行（建議 60~180 行）與 5,000 tokens 以內**；透過**省略測試（Omission Test）**剔除基礎模型已知常識，僅保留專案專屬決策點、步驟骨架與防呆紅線。
   - **`references/`（選配，單層按需靜態知識）**：存放長篇診斷矩陣、API 規格表、配置範本或專題手冊。**強制維持單層直接引用（1-Level Deep：`SKILL.md -> references/<topic>.md`）**，嚴禁 `ref_a.md -> ref_b.md` 多層巢狀跳轉；`SKILL.md` 引用處必須標明**明確的按需載入條件（在哪個步驟或何種條件下才讀取）**。任何超過 **100 行** 的 `references/*.md` 頂部必須配置 `## 目錄 (Contents)`，支援區段讀檔工具一次精準定位。
   - **`scripts/`（選配，決定性校驗與自動化腳本）**：**決定性校驗下沉腳本原則（Deterministic Validation Offloading）**——凡涉及精確字數/行數計算、複雜正則/AST 結構檢查、JSON Schema 驗證或固定格式轉換，應優先封裝為**非互動式且僅輸出精簡結果之**決定性 CLI 或 `scripts/` 可執行腳本，**避免強迫語言模型以純文字推理模擬機械式格式檢查**。
   - **`assets/`（選配，靜態輸出模板與結構資源）**：存放供複製或填空的報告骨架、配置檔樣板或固定結構資產，與說明性文檔（`references/`）分離。
2. **控制自由度校準與技術因果說明（Degrees of Freedom & Explain the Why）**：
   - **依脆弱度校準自由度**：高靈活度任務（如架構探索、優劣分析）採用**高自由度啟發式原則**；固定報告結構採用**中自由度參數化模板**；高風險或順序敏感操作（如編譯驗收、封包發布）採用**低自由度精確指令**。
   - **以因果說明取代教條大寫牆（Explain the Why）**：為關鍵限制附上 1 句簡短的底層技術原因（例如說明為何禁止裸換行或為何禁止跨技能點名），避免堆砌無脈絡的 `MUST` / `NEVER` 引發注意力稀釋（Instruction Dilution）。

## 3. 條件式工作流護欄與雙模輸出節流 (Conditional Workflow Guardrails & Output Routing)

並非所有技能皆為長鏈路多階段工程，工作流護欄必須依技能性質條件式配置：

1. **條件式檢核表與確認守門（Conditional Checklists & `Plan -> Validate -> Execute`）**：
   - **多步驟檢核表（Checklist）**：僅當技能包含 **3 個以上具相依性的執行步驟**時，於 `## 執行步驟` 開頭提供 `- [ ] 步驟 1...` 可勾選進度檢核表；單純規則攔截型或單步查詢型技能無須強塞檢核表。
   - **條件式確認守門與 End Turn**：僅在涉及**高風險修改、架構分支裁定、覆寫持久化資產或不可逆操作**時，強制先呈遞確認卡並 **立即 End Turn 等待開發者拍板**；純唯讀診斷、單步查詢或已獲明確授權之連續自動步驟不應無故中斷回合。
2. **雙模輸出節流（`Artifact-in-File` vs. `Artifact-in-Chat`）**：
   - **檔案落盤型技能（`Artifact-in-File` — 如計畫推進、代碼實作、專題報告落檔）**：實體產物已寫入磁碟檔案（SSOT），對話視窗**強制收斂為 5~10 行極簡狀態卡**（僅列產物路徑、核心結論摘要與下一步確認項），**嚴禁在對話中重複傾倒檔案全文**。
   - **對話直出型技能（`Artifact-in-Chat` — 如互動式教練引導、輕量狀態檢視、即時問答）**：交付物本身即為對話回應，應提供結構清晰、資訊完整的精煉解答，不受「5~10 行狀態卡」機械限制，但仍須避免無意義的冗長鋪陳。
3. **末置常見踩坑指南（`## 常見踩坑指南 (Gotchas)`）**：
   - 利用語言模型首尾注意力優勢（克服 Lost-in-the-Middle），於 `SKILL.md` 末尾統一設置 `## 常見踩坑指南 (Gotchas)`，集中提煉 2~5 條最違反直覺的實機環境陷阱與高頻錯誤模式，嚴禁將 Gotchas 外移至外部檔案。

## 4. 三層縱深安全控制、跨技能正交與路由驗證 (3-Layer Security & Orthogonality Verification)

1. **三層縱深安全控制（3-Layer Defense-in-Depth）**：
   - **第一層（文字契約層 Prompt Guardrails）**：於 `SKILL.md` 明訂禁止提示詞注入、禁止硬編碼憑證、禁止讀取敏感目錄（如 `~/.ssh`、`.env`）及 `[GATED]` 操作須獲當輪顯式授權。
   - **第二層（宿主工具權限層 Host Tool Permissions）**：文字禁令不能單獨視為硬性安全邊界；在支援工具權限宣告的宿主環境（如唯讀子代理沙盒、`allowed-tools` 白名單）中，唯讀探索或審查技能應同步收緊宿主工具權限。
   - **第三層（執行環境與 CLI 閘門層 Execution Gates）**：高風險或改變系統狀態的操作，必須結合決定性 CLI 檢核閘門（如 Schema check、dry-run compile、測試守門）通過後方可放行。
2. **跨技能職責正交與路由基準驗證（Cross-Skill Orthogonality & Routing Evaluation）**：
   - **職責正交與單一引用（DRY）**：新增或重構技能前，必須盤點相鄰技能的觸發邊界，避免兩個技能爭奪同一自然語言意圖；跨技能共用的規範條文（如代碼品質標準、技能設計標準）必須抽離為中央標準檔單點引用，嚴禁跨技能複製貼上。
   - **觸發與引用完整性驗證**：高關鍵度技能或修改 `description` 後，應透過正樣本（Should-Trigger）、近似負樣本（Near-Miss Should-Not-Trigger，特別檢驗軌跡 A 跨領域不誤觸與軌跡 B-Strict 一般討論不偷跑）及連結/語法靜態檢查驗證路由精準度。
