## 模式一：重寫高精準度 `description` 觸發條件（雙軌結構化邊界 A1 + B2）

將 `description` 控制在 1,024 字元內，並嚴格遵守三大黃金準則（詳見 [`SkillDesignStandards.md`](`__#{module://agents-workflow/assets/standards/SkillDesignStandards.md}__`) §1；若涉及 YSCB 動態標籤語法，請一併參照 [`YscbSkillDesignToolStandards.md`](`__#{module://agents-workflow/assets/standards/YscbSkillDesignToolStandards.md}__`)）：
1. **高密度關鍵詞前置**：語意濃縮、剔除冗餘形容詞與客套話，將核心動詞、支援標的與中英文同義觸發詞前置。
2. **自包含且具體可觀測**：不依賴外部未知脈絡（嚴禁「依循 xxx 規範」等隱含指涉），直接描述具體的「輸入標的、處理動作與輸出交付物」。
3. **雙軌結構化邊界（A1 + B2）**：
   - **軌跡 A — 被動／環境攔截型技能（Ambient / Intent-Driven Skills — A1 正向邊界契約）**：遵循**兩段式正向邊界** **`{核心用途、處理對象與交付物}。觸發情境：{具體動詞、目標檔案路徑特徵與前置攔截時機}。`**（預設不寫 `排除情境：`；僅於同領域極易混淆時選配補充無點名負向邊界，**嚴禁在 `description` 點名其他技能名稱 `(改用 xxx)`**）。
   - **軌跡 B — 主動指令型技能（Command-Driven / Slash-Invoked Skills — B2 分級命令鎖定）**：
     - **B-Strict（重型／破壞性指令）**：採用純斜線鎖定 **`{1 句話核心目的與交付物}。僅於顯式輸入 /{cmd} 時觸發，嚴禁主動觸發。`**。
     - **B-Assist（會話控制／教學輔助指令）**：採用 **`{1 句話核心目的與交付物}。僅於顯式輸入 /{cmd} 或明確要求{具體委託動作}時觸發。`**（省略內部步驟細節與 `/Cmd` 大小寫變體）。

**修改前（缺乏輸入輸出交付物、依賴外部隱含規範，且邊界模糊易與相鄰技能混淆）**：

```yaml
description: 知識庫與代碼規範手冊。依循專案規範管理文檔與恢復計畫進度。
```

**修改後（軌跡 A：被動／環境攔截型技能 — A1 聚合精簡正向邊界契約）**：

```yaml
description: 撰寫與審校 docs/ 系統知識庫文檔 (ARCHITECTURE/README/DESIGN_NOTES) 與公開 API Docstring。觸發情境：查閱或更新 docs/ 文檔、新增公開 API 註解、執行結案三層文檔對齊審查。
```

**修改後（軌跡 B-Strict vs. B-Assist：主動指令型技能分級契約）**：

```yaml
# B-Strict（重型重構／授權指令 — 純斜線鎖定，關閉自然語言後門）
description: 針對既有業務程式碼執行五維度靜態診斷、業務階段邏輯聚合與行為無損重構。僅於顯式輸入 /code-optimizer 時觸發，嚴禁主動觸發。

# B-Assist（會話控制／輔助指令 — 斜線＋明確委託雙通契約）
description: 讀取既有計畫之交接快照或階段產物以定位斷點並恢復開發進度。僅於顯式輸入 /continue 或明確要求接續既有開發計畫時觸發。
```

## 模式二：修復 YAML 特殊字元崩潰與保護動態佔位符

1. 若 `description` 以 `[!]`、`*`、`{` 等 YAML 保留字元開頭，務必加上雙引號包裹或移至文字中段。
2. 若受審檔案包含專案模板引擎的佔位符、跨檔案連結語法或 HTML 託管邊界註解，重構時必須 100% 保持其原有語法格式，切勿擅自刪改。

**修改前（未加雙引號導致 YAML 解析器崩潰）**：

```markdown
---
name: example-skill
description: [!] 授權守門技能。完全禁止主動觸發！
---
```

**修改後（合法 YAML 字串格式）**：

```markdown
---
name: example-skill
description: "授權守門技能 (Example)。僅當開發者顯式輸入 /example-skill 時觸發，完全禁止 Agent 於一般對話中主動觸發。"
---
```

## 模式三：剔除基礎模型常識與跨技能重複條文

- 刪除基礎概念介紹與通用套件安裝教學。
- 若次要技能重複抄寫了主樞紐技能的完整規則，應精簡為斷點速查表並透過連結委派予主樞紐技能。

## 模式四：漸進式揭露拆分（維持單層連結深度與明確載入條件）

當 `SKILL.md` 超過 500 行或附帶 `references/` 子目錄時，必須在 `SKILL.md` 明確標註**「在什麼條件下必須先讀取哪一份參考檔」**，且維持單層連結深度（`SKILL.md` -> `references/xxx.md`）。

**修改前（未說明何時讀取參考檔）**：

```markdown
本技能包含 `references/author_guide_and_checklist.md` 供參考。
```

**修改後（明確綁定動作觸發條件）**：

```markdown
- **情境 B：需要「撰寫／新增／修改」知識庫文檔，或執行結案三層文檔審查**：
  - **[!] 強制按需載入**：在動筆修改任何知識庫文檔前，**必須先讀取 [`references/author_guide_and_checklist.md`](./references/author_guide_and_checklist.md)**。
```

## 模式五：解除平台工具名硬編碼並提供唯讀降級備援

避免寫死單一 IDE 的工具函數名稱，並為 CLI 指令提供唯讀環境下的 Fallback 方案。

**修改前（寫死單一工具名且無 CLI 降級備援）**：

```markdown
請呼叫 `view_file` 讀取檔案，並執行專案狀態查詢 CLI。
```

**修改後（跨平台通用工具描述 ＋ CLI 降級備援）**：

```markdown
- **預設方式**：若環境支援終端執行，優先調用專案狀態查詢 CLI 取得計畫狀態大綱。
- **降級備援（Fallback）**：若處於純唯讀沙盒或 CLI 尚未就緒，直接以宿主內建的唯讀檔案檢視工具（如 `read_file`、`view_file` 或 `Read`）列出計畫目錄下的子目錄與最新檔案標頭。
```

## 模式六：校準控制自由度並補上因果理由 (Explain the Why)

將無解釋的死板禁令改為「規則 ＋ 1 句技術原因」，並對高風險指令採取低自由度約束。

```markdown
1. **零猜測熔斷**：需求語意不明或規格存在歧義時，**因為自行假設會造成後續階段連鎖返工**，禁止自行腦補，必須立即暫停向開發者釐清。
2. **指令單行化**：調用終端工具時**嚴禁字串夾帶未跳脫換行（`\n`）**，以防止 PTY 次級提示字元等待導致終端永久卡死。
```

## 模式七：植入進度檢核表與「規劃-驗證-執行」閉環

在多步驟工作流的 `## 執行步驟` 開頭加入可複製勾選的 Markdown 檢核表，並在寫入關鍵產物前加入自我驗證步驟。

````markdown
```markdown
/Pause 現場凍結檢核表：
- [ ] 步驟 1：定位當前正在進行的計畫目錄
- [ ] 步驟 2：讀取 handoff.md 模板，完整寫入現場狀態並驗證「重啟第 1 步」具體可執行
- [ ] 步驟 3：輸出極簡交接狀態卡並立即 End Turn
```
````

## 模式八：將環境陷阱收斂至 `## 常見踩坑指南 (Gotchas)`

在每份 `SKILL.md` 底部增設 `## 常見踩坑指南 (Gotchas)`，集中收錄 2~3 條最容易導致 Agent 執行偏差或合規失敗的非直覺陷阱。
