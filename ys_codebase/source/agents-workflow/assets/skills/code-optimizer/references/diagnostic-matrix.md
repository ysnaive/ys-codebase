## 1. 三級嚴重度判準與零處方榮譽結案守門 (Severity Tiers & Stop-Loss Gate)

診斷報告中所有發現之結構問題，強制按以下客觀標準分級：

- **`P0（高危破窗 / 正交職責混雜與資源競爭隱患 — 強烈建議優先修復）`**：
  - 模組間循環依賴（Cyclic Dependency）、跨模組直接篡改私有狀態、靜默吞噬例外（Silent Catch）、外部資源（檔案描述符/互斥鎖/子進程管道）未在異常或超時路徑確定性釋放、跨檔案錯誤調用契約（如將實例方法誤作靜態方法呼叫）、繞過專案核心安全或路徑抽象層、或**單一檔案/類別同時混雜多個正交變更軸線（Violating CCP/SRP，例如同時塞入底層協定解析、業務狀態機與終端/UI 渲染）**。
  - **[!] 反行數教條鐵律（Orthogonality over LOC）**：**檔案或函式行數僅作為初步探索時的關注參考訊號，絕非 `P0` 或 `S6` 定罪依據**！承載複雜領域規則但職責單一、共享同一把交易/執行緒鎖之狀態機、或針對同一 `Report` 依序執行的線性檢查管線，即使行數較多亦**不屬於 `D1/P0` 缺陷，嚴禁強行拆檔**。
- **`P1（結構耦合 / 可維護性阻礙 — 標準重構目標）`**：
  - 頂層公開方法混雜宏觀業務編排與底層細節（違反 SLAP）、類別內大量方法未讀寫實例狀態卻與有狀態生命週期強綁定（或 `S2` 抽離後殘留 1 行無意義轉發殼層）、跨方法重複出現同構控制流骨架、超過 3~4 層深層巢狀（Arrow Anti-pattern）、長參數列或以鬆散非結構化字典跨階段傳遞關鍵狀態（或跨多個 `partial class` 分部檔散落共享大量私有快取欄位）、或經 `callers + search` 雙重查證確認 0 引用的孤兒死代碼（Dead Code）。
- **`P2（局部異味 / 可讀性打磨 — 順手收斂項目）`**：
  - 散落的魔術常數（Magic Literals）、可透過提取具名階段函式消除的段落分隔註解、殘留於註解中的歷史審計/工單編號（如 `(F-01)`、`[P00:DR-01]`）、或局部冗餘的中間變數與過時廢棄註解塊。

> [!IMPORTANT]
> **🏆 零 P0/P1 收斂榮譽結案守門（Convergence Stop-Loss Gate — 杜絕湊數強迫症）**：  
> 當受檢檔案或模組結構已高度內聚，若檢出之 **`P0 = 0`（或 `P0 = 0` 且 `P1 = 0`，僅餘零星 `P2` 微調）**，診斷報告必須誠實標記各維度為 `Pass`，並於結論直接給出 **「模組已達最佳內聚度，推薦選擇【出口 ③ 維持現狀結案】(`Conclude — No Further Refactoring Required`)」**。將「誠實判定無須重構」視為與「開立處方」同等價值的專業產出，**絕對禁止為了不交白卷而違反四大防過度設計紅線強湊拆檔或抽象基類**！

## 2. 跨語言五維度靜態診斷矩陣 (D1 ~ D5)

| 維度代號 | 診斷維度名稱 | 核心審查指標（跨語言通用軟工抽象） | 典型病徵與審查檢核點 | 對應重構策略 |
| :---: | :--- | :--- | :--- | :---: |
| **`D1`** | **職責內聚與抽象層級**<br>*(Cohesion & Abstraction Levels)* | • 單一職責與共同封閉原則 (SRP / CCP)<br>• 單一抽象層級原則 (SLAP)<br>• 有狀態實體與無狀態運算分離 | 1. **正交職責混雜 (True God Class/File)**：單一檔案同時塞入正交變更軸線（如資料模型、底層 I/O 解析與高階業務/UI 渲染；注意：僅以行數多但職責單一之狀態機/線性管線不在此列）。<br>2. **抽象層級混雜**：公開入口函式內同時出現高階業務步驟與底層正規表達式切割、位元操作或 I/O 緩衝細節。<br>3. **假性實例方法與 `partial class` 偽拆檔**：類別中存在完全不讀寫實例欄位（`self` / `this`）的純運算方法；或雖拆為多個 `partial class` 檔案，卻跨分部檔直接散落讀寫數十個同生命週期私有快取欄位。 | `S1`, `S2`, `S5`, `S6` |
| **`D2`** | **調用耦合與拓撲健康度**<br>*(Coupling & Topology Hygiene)* | • 入向/出向耦合度 (Ca / Ce)<br>• 無環依賴原則 (ADP)<br>• 雙重查證死代碼與轉發殼清零 | 1. **雙向或環狀依賴**：模組 A 匯入模組 B，同時模組 B 又反向匯入模組 A（含方法內延遲循環匯入）。<br>2. **殘留轉發殼層與過度暴露**：`S2`/`S6` 抽離後在原類別殘留 1 行 `staticmethod` / `private static` 轉發殼，或在 `Mode A` 下殘留相容別名。<br>3. **孤兒死代碼 (Dead Code — 強制雙重查證)**：經全空間 **`callers` + 全文 `search` 雙重查驗**，確認無任何生產、測試、POCO 欄位/泛型 `<T>` 型別宣告、基底多型虛擬分派、`[InternalsVisibleTo]` 或 Source Generator 引用之廢棄符號。 | `S2`, `S6` |
| **`D3`** | **控制流與認知複雜度**<br>*(Control Flow & Cognitive Complexity)* | • 圈複雜度與認知複雜度<br>• 縮排深度上限 ($\le 3$ 層)<br>• 結構性重複收斂 (DRY) | 1. **箭頭型深層巢狀 (Arrow Anti-pattern)**：`if / for / try` 連續縮排超過 3~4 層，核心主邏輯被擠在最內層。<br>2. **多階段交織長程序 (Multi-Stage Procedure)**：單一函式包含多個隱含業務階段且透過大量局部可變變數交織狀態。<br>3. **同構樣板散落**：多個業務方法重複編寫相同的「前置檢查 $\to$ 資源獲取 $\to$ 錯誤轉換 $\to$ 清理」骨架。 | `S1`, `S3`, `S4` |
| **`D4`** | **介面契約與資源生命週期**<br>*(Contracts & Resource Lifecycle)* | • 靜態型別簽名完整性<br>• 異常傳播透明性<br>• 確定性資源釋放 (RAII / Scoped) | 1. **鬆散容器與長參數列**：函式超過 5~6 個散裝參數，或以無型別約束之裸字典 (`dict` / `Map` / `any`) 跨多階段讀寫業務狀態。<br>2. **異常掩蓋與契約變異**：空白或過寬的例外捕捉塊吞掉底層錯誤，或回傳型別隨參數變異導致呼叫端型別不安全。<br>3. **資源洩漏與併發競爭**：檔案控制代碼、暫存目錄、互斥鎖或子進程管道未置於 `with` / `using` / `defer` / `try...finally` 保護中，或非同步執行緒超時後未清理持續爭搶管道。 | `S3`, `S5` |
| **`D5`** | **架構邊界與專案慣例**<br>*(Architectural Idioms)* | • 基礎設施抽象層遵從度<br>• 常數與組態集中化<br>• 依賴層級隔離紀律 | 1. **繞過宿主基礎設施**：未遵循專案統一的虛擬路徑/檔案代理層（如 `vfs` / `uri`）、日誌或組態介面，直接硬編碼相對路徑或重複手寫尋根/原子寫入邏輯。<br>2. **魔術常數與工單註解污染**：業務邏輯中硬編碼超時秒數、緩衝區大小；或源碼註解殘留 `(F-01)`、`[P00:DR-01]` 等審計編號噪音。<br>3. **跨層反向耦合**：底層核心模組反向依賴上層選配業務模組（含注入於 `CODE_OPTIMIZER_STANDARDS` 之專案特化規則）。 | `S5`, `S6` |

## 3. R{NN} 調研診斷報告 (`R{NN}_code_optimization_audit.md`) 結構指引

> [!CAUTION]
> **🚨 強制對齊 `RXX_research_report.md` 四大標準 H2 標題（防範 `plan verify` 退件鐵律）**：  
> `agents-workflow plan verify` 會剛性檢核所有 `R{NN}_*.md` 檔案是否包含 [`RXX_research_report.md`](`__#{module://agents-workflow/assets/templates/RXX_research_report.md}__`) 模板定義的 **4 個標準二級標題 (`## 1.` ~ `## 4.`)**！  
> 因此，撰寫 `R01_code_optimization_audit.md`（或跨代盲審 `R02`/`R03`）時，**頂層 `##` H2 標題必須 100% 保持模板原貌**，並將 `code-optimizer` 專屬的五個診斷區塊作為 **`###` 三級子標題 (H3)** 掛載於對應的 H2 之下（嚴禁自創頂層 H2 標題取代模板 H2）：

```markdown
## 1. 背景與調研目標 (Background & Objectives)
### 1.1 定錨基準與範圍摘要
- 記錄開發者拍板之「檢視範圍」、「生命週期模式 (Mode A / Mode B)」、「代理執行軌道」與現行測試基線狀態。

## 2. 候選方案分析與對比 (Candidate Evaluation)
### 2.1 契約邊界與內部工具函式查驗表
- 明確列出「公開契約入口清單（Mode A 預計收斂為單一入口並同步改寫之調用點 / Mode B 預計保留門面重匯出之符號）」與「經 callers + search 雙重查證確認 0 外部引用之純內部工具函式/死代碼清單」。
### 2.2 重構深度候選方案對比
- 對比候選重構方案（或當 P0=0, P1=0 時評估維持現狀直接結案）。

## 3. 架構設計與驗證 (Architecture & PoC)
### 3.1 D1 ~ D5 五維度分級診斷矩陣
- 逐一列出 D1~D5 檢查結果表格（檔案路徑:行號區間 | 維度 | P0/P1/P2 | 具體結構病徵 | 對應策略；無異常標記 Pass）。
### 3.2 S1 ~ S6 外科手術重構處方箋 (Refactoring Blueprint)
- 具體說明預計提取之階段函式 (S1)、無狀態純函式剝離與零轉發殼清理 (S2)、同構合併與 20% 邊界不變量保護 (S3)、控制流扁平化 (S4)、資料團塊封裝 (S5) 與正交拆檔評估 (S6)。

## 4. 調研結論與落地建議 (Conclusion & Recommendation)
### 4.1 風險評估與推薦流轉出口
- 明確給出推薦流轉出口（出口 ① 原地升級 Fast Track / Full Track / Umbrella、出口 ② 轉入 Roadmap/Todo、或出口 ③ P0=0/P1=0 維持現狀結案）。
```
