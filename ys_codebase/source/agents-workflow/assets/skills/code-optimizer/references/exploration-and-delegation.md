## 1. 包含式三層範圍探索策略 (Inclusive Scope Hierarchy)

`code-optimizer` 的檢視範圍遵循**「大範圍向上包含小範圍（`全專案 ⊃ 單一模組 ⊃ 單一檔案`）」**原則——選擇大範圍時，絕不代表僅看表層跨檔案連線而略過單檔內部的邏輯腐化，而是由微觀至宏觀層層涵蓋：

| 開發者選定範圍 | 微觀單檔/類別層級分析（必含） | 中觀模組/子系統層級分析 | 宏觀跨模組/全專案層級分析 |
| :--- | :--- | :--- | :--- |
| **① 特定檔案 / 小範圍 (`File Scope`)** | 針對目標檔案執行 `D1~D5` 審查，識別過長方法的業務階段（供 `S1` 拆解）、未讀寫實例狀態的方法（供 `S2` 無狀態剝離）、重複骨架（`S3`）、深層巢狀（`S4`）、長參數群（`S5`）及正交職責拆分點（`S6`）。 | 查驗該檔案對外暴露符號之入向調用點（Callers & Lexical References）。 | N/A |
| **② 單一模組 (`Module Scope`)** | **完整包含 ① 對模組內各業務檔案之 `S1~S6` 微觀診斷**。 | 盤點模組內跨檔案耦合拓撲（`D2` 循環依賴解除、模組內死代碼）、跨檔重複樣板與共用資料結構抽離（`S3`/`S5`）、子模組物理拆分（`S6`）與模組公開 API 入口收斂。 | 查驗外部模組對本模組匯出符號之跨模組入向調用點與測試引用。 |
| **③ 全專案 / 多模組 (`Project Scope`)** | **完整包含 ① 對各模組內部關鍵業務檔案之 `S1~S6` 微觀診斷**。 | **完整包含 ② 對各模組內部跨檔耦合與入口契約之分析**。 | 掃描跨模組邊界違規（`D5` 繞過統一基礎設施抽象）、跨模組孤兒死代碼、公共抽象重複造輪子，並產出全專案重構優先級熱點矩陣。 |

## 2. 基於開發者指定 Mode A / Mode B 之調用圖譜與死代碼雙重查驗規則

生命週期模式（`Mode A` 或 `Mode B`）由開發者於步驟 1 顯式拍板鎖定（**嚴禁 Agent 或子代理自行猜測模組是否已對外釋出**）。探索階段須依據已鎖定之模式，執行對應的調用圖譜與契約邊界查驗：

### 2.1 當開發者指定 `Mode A：收斂期 / 允許破壞性清理 (Convergence Mode)`
- **核心目標**：消除一切歷史過渡包袱，強制收斂為**單一正統入口（Single Canonical Entry）**。
- **探索查驗動作**：
  1. 找出目標範圍內所有的相容別名（Aliases）、薄轉發包裝函式（Pass-through Wrappers）、過時參數分支與冗餘抽象基類。
  2. 透過環境檢索工具（如具備 AST 圖譜環境下之 `callers` / `impact`，搭配全文/符號 `search`）收集所有內部、跨模組、範例（`samples/`）與測試（`tests/`）調用點座標，列入 **「需同步改寫之調用方清單（Callers to Update）」**，於實作階段一併改寫並物理刪除舊入口。

### 2.2 當開發者指定 `Mode B：維護期 / 嚴守向下相容 (Compatibility Mode)`
- **核心目標**：對外公開契約 100% 零破壞，同時對**經嚴格查證之純內部工具函式**直接進行破壞性收斂，杜絕在內部堆疊轉發垃圾。
- **雙層嚴格查驗規則（Strict Two-Tier Verification in Mode B）**：
  1. **第一層 — 對外公開契約與跨模組入口（Public / Exported Surface -> 強制門面保護）**：
     - **判定條件**：凡列於模組公開匯出清單（如 `__all__`、`index` / `__init__` 匯出、Public Header、或插件註冊表如 `contributes/*.json`），**或**經全空間檢索發現存在跨模組入向調用之符號。
     - **處置原則**：當內部執行 `S1~S6` 重構或物理拆檔時，原公開入口必須透過**門面重匯出（Facade Re-export）**或薄轉發層維持原簽名、參數預設值與回傳/異常契約 100% 相容。
  2. **第二層 — 經嚴格查驗確認之純內部工具函式/私有結構（Strictly Verified Internal Helpers -> 直接破壞性收斂）**：
     - **嚴格判定條件（須同時滿足）**：
       - ① **非對外公開契約**：未列於任何公開匯出介面、插件註冊點或外部文檔契約；
       - ② **全空間 0 外部調用鐵證**：經全專案範圍之調用圖譜（`callers`）與文字檢索（`search`）雙重確認，**100% 僅在當前檔案或當前模組內部被調用（0 外部跨模組引用）**。
     - **處置原則**：**直接比照 `Mode A` 執行破壞性變更**（直接重命名、合併同構函式、剝離無狀態邏輯、收斂參數型別或物理刪除，並同步更新模組內部的調用點），**絕對禁止為純內部工具函式保留相容別名或轉發死代碼**！

### 2.3 [!] 靜態強型別、多型、欄位與代碼生成之「死代碼雙重查證鐵律 (Call-Graph + Lexical Search Gate)」
在 C++ / C# / TypeScript / Rust / Java / Python 等語言中，AST 調用圖譜（如 `knowledge-db callers <Symbol>`）僅追蹤**直接靜態函式呼叫邊 (`CALLS`)**，回傳 `0` **絕不等於 0 引用**！在將任何符號列入 `D2` 殭屍死代碼拔除清單前，**強制執行雙重檢索守門**：
1. **哪些符號不可僅憑 `callers == 0` 定罪**：
   - 純資料型別宣告（`class` / `struct` / `enum` / `interface` / `POCO` / `DTO`）：常被用作欄位型別（`private MyAsset _asset;`）、函式參數或泛型型別參數（`LoadAsset<MyAsset>()`）。
   - 多型虛擬方法與模板轉發（C++/C# `virtual` / `override` 方法、C++ 模板基類內部轉發）：呼叫端通常持有基底類別指標/介面（`base_ptr->update()`）。
   - 靜態/內部欄位與屬性（`static` / `internal` Fields & Properties）、常數、以及供測試驗證之探針計數器（如 `[InternalsVisibleTo]` 暴露給 `tests/` 直接讀寫之欄位）。
   - 具備 `[Attribute]` / `@Decorator` 反射實體化、JSON 序列化契約或編譯期 Source Generator（如 Roslyn Generator）動態合成呼叫之符號。
2. **強制驗證動作**：凡 `callers == 0` 之上述符號，**必須強制追加執行一次跨生產碼與 `tests/` 的全文/符號檢索（如 `knowledge-db search "<SymbolName>" --json`）**，確認全倉（含測試與泛型 `<T>`）真為 0 引用後，方可定案刪除。

## 3. 多軌代理執行模式與調度上限 (Multi-Track Execution & Batch Cap)

為兼顧不同開發者的 **Token 額度預算** 與 **大型專案吞吐量需求**，代理執行模式由開發者於步驟 1 顯式選定，嚴禁未經詢問擅自派發大量子代理：

| 範圍層級 | 可選執行軌道（由開發者於步驟 1 指定） | 運作方式與適用時機 |
| :--- | :--- | :--- |
| **單一檔案 / 小範圍 (`File Scope`)** | **`[軌道 1] 固定主代理內聯執行`** | 固定由主代理直接以大綱檢索與 `__%{agent_tool.file_read_range}__` 分段精讀、產出 `R01` 並執行重構，免除子代理冷啟動成本。 |
| **單一模組 (`Module Scope`)** | **`[軌道 2A] 純主代理內聯審查`**<br>*(Token 節流型)* | 全程由主代理在當前對話視窗內按階段檢索、撰寫 `R01` 與執行重構；適合 Token 額度較小或希望逐步細審之開發者。 |
| **單一模組 (`Module Scope`)** | **`[軌道 2B] 主代理 + 盲眼子代理`**<br>*(Context 隔離與盲審型)* | 主代理委派唯讀/盲審子代理進行模組掃描、反向查驗或 `R02` 盲測，將探索期原始碼隔離於子代理視窗外。 |
| **全專案 / 多模組 (`Project Scope`)** | **`[軌道 3A] 主代理序列滾動推進`**<br>*(`sub_n` 完成後才進 `sub_n+1`，Token 節流型)* | 建立 Umbrella 主計畫後，由主代理**單執行緒逐一推進**：先完整跑完 `sub_01`（診斷 $\to$ 重構 $\to$ 單模編譯測試通過），再啟動 `sub_02`。每輪 Token 消耗極低且完全不會發生跨模組平行改檔競態。 |
| **全專案 / 多模組 (`Project Scope`)** | **`[軌道 3B] 主代理統籌 + N 路盲眼子代理平行推進`**<br>*(高吞吐多代盲審型)* | 建立 Umbrella 主計畫後，按模組平行派發子代理各自負責 `sub_XX` 的診斷落檔與代碼重構；子代理期間**禁止各自執行全專案編譯/耗時測試**（避免搶鎖），待全數進入 `P06` 後由主代理統一編譯驗證。 |

### [!] 子代理平行調度三大安全鐵律（適用於選用 `軌道 2B` 或 `軌道 3B` 時）
1. **單回合平行派發上限 (`Batch Size Cap: 3~4 Subagents/Turn`)**：
   - 當子計畫數量超過 4 個（例如 5~8 個模組）時，主代理在單一 Turn 內同時呼叫子代理工具的數量**上限為 3~4 個**（須分 2 個以上 Turn 分批派發）。
   - **原因**：單回合同時序列化 5~8 個長篇子代理呼叫極易觸發底層模型輸出長度溢出與 JSON 閉合迴圈崩潰。
2. **極簡指針 Prompt 原則 (`Pointer-Only Prompting`)**：
   - 派發實作或盲審子代理時，傳入之 Prompt 必須極簡（僅給定目標子計畫目錄路徑、負責之源碼目錄邊界、鎖定之 `Mode A/B` 與技能手冊路徑），**嚴禁在 Prompt 參數中複製貼上數百行的 `R01` 處方明細**。
3. **跨模組 `Mode A` 兩階段交接表 (`[Cross-Module Mode A Handoff]`)**：
   - 在 `軌道 3B` 平行實作下，各子代理僅能修改自身負責模組之目錄。若子代理在 `Mode A` 下刪除或重命名了會被**其他子計畫、`samples/` 或 `tests/`** 呼叫的符號，子代理必須在完成回條中附帶標準化的 **`[Cross-Module Mode A Handoff]` 簽名對照表（`舊符號 -> 新正統符號 + 外部調用座標`）**，交由主代理在啟動統一編譯前一次批次對齊外部呼叫點。

## 4. 子代理雙模回傳契約與跨代盲審協議 (Dual-Mode Return Schema & Blind Audit)

當開發者選擇使用子代理（`軌道 2B` 或 `軌道 3B`）時，依任務規模採以下雙模回傳契約，並支援高階跨代盲審：

### 4.1 雙模回傳契約（Mode I vs. Mode II）
- **模式 I（Single-Plan 局部切片探索 — 由主代理撰寫 `R{NN}`）**：
  - 子代理純唯讀（禁碰 `__${project://plans}__/`），向主代理回傳 **$\le 400$ Tokens** 之結構化摘要：① 契約邊界盤點清單（`Mode A` 待拔除入口與調用點 / `Mode B` 凍結門面 vs. 0 外部調用內部函式）、② 業務階段與無狀態方法清單（供 `S1`/`S2`）、③ `D1~D5` 病灶座標表（`檔案:行號 | 維度 | P0/P1/P2 | 病徵 | S1~S6`）、④ 既有測試路徑與命令。
- **模式 II（Umbrella 多子計畫模組級獨立審計 — 授權子代理直接落檔 `sub_XX/R{NN}`）**：
  - 在涵蓋多模組、上百個檔案之 Umbrella 計畫中，為避免壓縮摘要遺失行號細節或塞爆主代理視窗，**授權各子計畫子代理直接將完整診斷報告寫入 `sub_XX/R{NN}_code_optimization_audit.md`**，並僅向主代理回傳 **$< 50$ Tokens 的極簡驗收收據**（例：`sub_01 R01 已落檔 | P0: 1, P1: 4, P2: 2 | 核心處方：S1/S2/S6`）。

### 4.2 跨代零錨定盲審收斂協議 (`R{NN}` Blind Convergence Audit)
當首輪（`R01`）重構完成並通過測試後，若開發者希望執行第二代/第三代盲審（`R02` / `R03`）進行 A/B 收斂驗證，派發盲審子代理時必須嚴守 **「三不零錨定鐵律 (Zero-Anchoring Rules)」**：
1. **禁讀既有計畫產物**：嚴格禁止盲審子代理讀取 `__${project://plans}__/` 目錄下任何已落檔之 `P00~P07`、`R01`、`fast_track_plan` 或 `changelog.md`，強制以 100% 全新視角直接掃描當前工作區源碼。
2. **零方向暗示 Prompt**：提供給盲審子代理的提示詞僅能包含「任務目標、負責模組目錄邊界、鎖定之 `Mode A/B`、以及產出檔名 `R{NN}_code_optimization_audit.md`」，**嚴禁給予任何具體病灶方向提示**。
3. **誠實收斂判定（杜絕湊數強迫症）**：明確告知盲審子代理——若該模組經前輪重構後已高度內聚，**允許且鼓勵判定 `P0 = 0`（甚至 `P1 = 0`）並建議直接結案**，嚴禁為填滿表格而強拆高內聚檔案。
