## 1. 包含式三層範圍探索策略 (Inclusive Scope Hierarchy)

`code-optimizer` 的檢視範圍遵循**「大範圍向上包含小範圍（`全專案 ⊃ 單一模組 ⊃ 單一檔案`）」**原則——選擇大範圍時，絕不代表僅看表層跨檔案連線而略過單檔內部的邏輯腐化，而是由微觀至宏觀層層涵蓋：

| 開發者選定範圍 | 微觀單檔/類別層級分析（必含） | 中觀模組/子系統層級分析 | 宏觀跨模組/全專案層級分析 |
| :--- | :--- | :--- | :--- |
| **① 特定檔案 / 類別 (`File Scope`)** | 針對目標檔案執行 `D1~D5` 審查，識別過長方法的業務階段（供 `S1` 拆解）、未讀寫實例狀態的方法（供 `S2` 無狀態剝離）、重複骨架（`S3`）、深層巢狀（`S4`）、長參數群（`S5`）及巨型檔案拆分點（`S6`）。 | 查驗該檔案對外暴露符號之入向調用點（Callers）。 | N/A |
| **② 單一模組 (`Module Scope`)** | **完整包含 ① 對模組內各業務檔案之 `S1~S6` 微觀診斷**。 | 盤點模組內跨檔案耦合拓撲（`D2` 循環依賴解除、模組內死代碼）、跨檔重複樣板與共用資料結構抽離（`S3`/`S5`）、子模組物理拆分（`S6`）與模組公開 API 入口收斂。 | 查驗外部模組對本模組匯出符號之跨模組入向調用點。 |
| **③ 全專案 (`Project Scope`)** | **完整包含 ① 對各模組內部關鍵業務檔案之 `S1~S6` 微觀診斷**。 | **完整包含 ② 對各模組內部跨檔耦合與入口契約之分析**。 | 掃描跨模組邊界違規（`D5` 繞過統一基礎設施抽象）、跨模組孤兒死代碼、公共抽象重複造輪子，並產出全專案重構優先級熱點矩陣。 |

## 2. 基於開發者指定 Mode A / Mode B 之調用圖譜與內部工具函式查驗規則

生命週期模式（`Mode A` 或 `Mode B`）由開發者於步驟 1 顯式拍板鎖定（**嚴禁 Agent 或子代理自行猜測模組是否已對外釋出**）。探索階段須依據已鎖定之模式，執行對應的調用圖譜與契約邊界查驗：

### 2.1 當開發者指定 `Mode A：收斂期 / 允許破壞性清理 (Convergence Mode)`
- **核心目標**：消除一切歷史過渡包袱，強制收斂為**單一正統入口（Single Canonical Entry）**。
- **探索查驗動作**：
  1. 找出目標範圍內所有的相容別名（Aliases）、薄轉發包裝函式（Pass-through Wrappers）、過時參數分支與冗餘抽象基類。
  2. 透過環境檢索工具（如具備 AST 圖譜環境下之 `callers` / `impact`，或靜態引用搜尋）收集所有內部與跨模組調用點座標，列入 **「需同步改寫之調用方清單（Callers to Update）」**，於實作階段一併改寫並物理刪除舊入口。

### 2.2 當開發者指定 `Mode B：維護期 / 嚴守向下相容 (Compatibility Mode)`
- **核心目標**：對外公開契約 100% 零破壞，同時對**經嚴格查證之純內部工具函式**直接進行破壞性收斂，杜絕在內部堆疊轉發垃圾。
- **雙層嚴格查驗規則（Strict Two-Tier Verification in Mode B）**：
  1. **第一層 — 對外公開契約與跨模組入口（Public / Exported Surface -> 強制門面保護）**：
     - **判定條件**：凡列於模組公開匯出清單（如 `__all__`、`index` / `__init__` 匯出、Public Header、或插件註冊表如 `contributes/*.json`），**或**經全空間檢索發現存在跨模組入向調用之符號。
     - **處置原則**：當內部執行 `S1~S6` 重構或物理拆檔時，原公開入口必須透過**門面重匯出（Facade Re-export）**或薄轉發層維持原簽名、參數預設值與回傳/異常契約 100% 相容。
  2. **第二層 — 經嚴格查驗確認之純內部工具函式/私有結構（Strictly Verified Internal Helpers -> 直接破壞性收斂）**：
     - **嚴格判定條件（須同時滿足）**：
       - ① **非對外公開契約**：未列於任何公開匯出介面、插件註冊點或外部文檔契約；
       - ② **全空間 0 外部調用鐵證**：經全專案範圍之調用圖譜（如 `callers`）與文字檢索雙重確認，**100% 僅在當前檔案或當前模組內部被調用（0 外部跨模組引用）**。
     - **處置原則**：**直接比照 `Mode A` 執行破壞性變更**（直接重命名、合併同構函式、剝離無狀態邏輯、收斂參數型別或物理刪除，並同步更新模組內部的調用點），**絕對禁止為純內部工具函式保留相容別名或轉發死代碼**！

## 3. 支柱一唯讀探索子代理量化觸發門檻與環境路由

為保護主代理（Main Agent）的 Context Window 不被大量探索期原始碼淹沒，同時避免對微型目標產生不必要的子代理冷啟動延遲，採以下量化路由：

- **直接由主代理內聯探索（Inline Funnel Retrieval）**：
  - **條件**：目標為**單一檔案（`File Scope`）且行數 $\le 400$ 行**，或當前宿主環境不支援子代理。
  - **動作**：主代理先以大綱檢索取得符號與行號座標，再以 `__%{agent_tool.file_read_range}__` 分段精讀，並查詢上游調用點。
- **委派支柱一唯讀探索子代理（Pillar 1 Read-Only Exploration Subagent）**：
  - **條件**：目標為 **全專案（`Project Scope`）**、**單一模組（`Module Scope` 且 $\ge 3$ 個檔案）**、**單檔 $> 400$ 行**，或需追蹤跨模組多階調用鏈。
  - **調度鐵律**：
    1. **純唯讀隔離**：明確指示子代理**僅允許使用唯讀檢索與檔案讀取工具（`__%{agent_tool.file_read_range}__`）**，嚴禁修改任何檔案、嚴禁觸碰 `__${project://plans}__/` 目錄、嚴禁執行耗時的測試套件。
    2. **平行分治（全專案範圍）**：若範圍為 `Project Scope`，主代理可按模組平行派發多個唯讀探索子代理，各自負責單一模組的 `D1~D5` 掃描與 `S1~S6` 階段分析。

## 4. 探索子代理高密度回傳契約 (Subagent Return Schema)

主代理派發探索子代理時，強制要求子代理**嚴禁回傳大段原始碼切片**，總回傳篇幅控制在 **$\le 400$ Tokens**，僅回傳以下四項結構化資訊：

1. **契約邊界盤點清單（依開發者指定之 `Mode A` 或 `Mode B`）**：
   - 若為 `Mode A`：列出可物理拔除之冗餘入口/別名，以及需同步更新的所有調用方座標（`檔案:行號`）。
   - 若為 `Mode B`：區分列出 **「[凍結門面] 需保留相容匯出之公開符號清單」** 與 **「[已嚴格查證 0 外部調用] 可直接破壞性收斂之純內部工具函式清單」**。
2. **類別/模組業務階段與狀態依賴圖（供 `S1` & `S2`）**：
   - 針對肥大類別或長方法，標註可切分的業務邏輯階段名稱（供 `S1` 提取階段輔助函式），以及**未讀寫任何實例狀態（Instance Fields）、可剝離為模組私有純函式的方法清單**（供 `S2` 無狀態剝離）。
3. **`D1~D5` 病灶座標表**：
   - 以 Markdown 表格列出：`檔案路徑:起訖行號` | `維度 (D1~D5)` | `嚴重度 (P0/P1/P2)` | `具體結構病徵` | `建議重構策略 (S1~S6)`。
4. **現有測試對應關係**：
   - 對應保護該模組/檔案的既有測試檔案路徑與測試驗證命令。
