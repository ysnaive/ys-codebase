# 文檔資料庫系統規範 (Documentation Standards)

本文件定義專案中 `docs/` 知識庫目錄的架構、維護原則與操作規範。

---

## 核心定位：兩套系統的職責劃分

| 系統 | 路徑 | 職責 | 內容性質 |
| :--- | :--- | :--- | :--- |
| **開發過程紀錄** | `{plans_dir}` / `{archive_dir}` | 開發軌跡、Decision Records、Phase 推進 | 過程導向，完成後歸檔凍結 |
| **知識庫（當前事實）** | `docs/` | 系統當前狀態：架構、機制、邊界條件、工程妥協 | 狀態導向，隨系統演進持續更新 |

> [!IMPORTANT]
> **知識庫只陳述事實，不記錄決策過程。**
> 「為什麼這樣設計」的辯論留在 `{plans_dir}` 的 Decision Records。
> `docs/` 只回答「現在是什麼樣子」與「你需要知道的邊界條件與坑點」。

---

## 1. 目錄結構與鏡像原則

### 1.1 剛性鏡像原則
`docs/` 實體資料夾路徑應與專案原始碼的模組/命名空間 (Component / Namespace) 保持 1:1 結構鏡像。

### 1.2 全域與特化目錄
使用底線前綴（`_`）的目錄為**非模組的特化目錄**：
```text
docs/
├── README.md                   ← 全局知識庫總導覽頁 (Knowledge Map)
├── _global/                    ← 全域系統架構文件（系統全貌圖、通訊架構圖等）
├── _project/                   ← 專案層級規範（環境建置、程式風格 coding-standards.md、Git 流程）
└── [模組鏡像路徑]/            ← 鏡像對應源碼模組的知識庫目錄
```

## 2. 四種標準文檔類型

| 檔案 | 必備/選用 | 職責 | 建立時機 |
| :--- | :--- | :--- | :--- |
| `README.md` | **必備** | 模組首頁：職責邊界、架構概覽圖、導覽目錄 | 模組建立時立即建立 |
| `[topic].md` | **按需** | 特定主題深度說明（演算法原理、生命週期等） | 當某主題過長使 README 超過 2 頁時 |
| `DESIGN_NOTES.md` | **選用** | 工程妥協記錄：非直觀設計、效能/硬體/平台限制 | 有非顯而易見的工程取捨時 |
| `CHANGELOG.md` | **選用** | 重大架構重構歷史（僅記錄架構級變更與痛點） | 發生重大架構重構時 |

## 3. Frontmatter Schema

所有 `docs/` 下的 Markdown 文件**必須**包含以下 YAML Frontmatter：

```yaml
---
# ── 識別資訊 ─────────────────────────────────────────
target: "[模組名稱或 Namespace，例：Core/Application]"
doc_type: "readme | topic | design_notes | changelog | overview"

# ── 狀態 ─────────────────────────────────────────────
status: "draft | active | deprecated | archived"

# ── 來源連結 ──────────────────────────────────────────
source_paths:
  - "[對應之原始碼檔案路徑]"
related_docs:
  - "./DESIGN_NOTES.md"

# ── 維護資訊 ──────────────────────────────────────────
last_updated: "YYYY-MM-DD"
---
```

## 4. 知識點提煉與 Alert 等級

| Alert 等級 | 使用場景 |
| :--- | :--- |
| `[!CAUTION]` | 可能導致重大 Bug、硬體損壞、記憶體洩漏或安全漏洞的關鍵坑點 |
| `[!WARNING]` | 常見誤用模式，影響穩定度或效能的注意事項 |
| `[!NOTE]` | 非顯而易見但重要的設計細節（解釋 Why） |
| `[!TIP]` | 推薦的最佳實踐與呼叫技巧 |
