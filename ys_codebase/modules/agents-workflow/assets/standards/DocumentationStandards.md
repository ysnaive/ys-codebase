# 專案知識庫架構與維護規範 (Documentation Standards)

本文件定義專案知識庫 (`docs://`) 的 7 大抽象知識維度、判定決策樹、中觀專題手冊與 1:1 交付驗收原則。

---

## 1. 知識庫 7 大抽象維度體系 (The 7-Dimension Taxonomy)

專案文檔應嚴格按照以下 7 大抽象層次組織，維持事實與歷史討論的清晰分離：

| 維度編號 | 維度名稱 | 核心語意與職責 | 目標檔案與路徑 |
| :---: | :--- | :--- | :--- |
| **維度 1** | 系統/模組概覽 | 模組定位、高階架構圖、核心職責與邊界說明。 | `docs/<Module>/README.md` |
| **維度 2** | 快速起步與指南 | 開發者安裝、CLI 快速上手與最簡使用範例。 | `docs/<Module>/QUICKSTART.md` |
| **維度 3** | 中觀專題手冊 (Topic Docs) | 深入單一專題（狀態機、通訊協議、依賴注入流水線等）。 | `docs/<Module>/[TOPIC].md` |
| **維度 4** | 介面與 API 參考 | 公開 API 簽名、參數型別、回傳值契約與例外說明。 | `docs/<Module>/API_REFERENCE.md` |
| **維度 5** | 設計決策與工程妥協 | 記錄非直觀實作、歷史妥協與 `[DN-XX]` 標記。 | `docs/<Module>/DESIGN_NOTES.md` |
| **維度 6** | 部署與環境配置 | 環境變數、設定檔 Schema 與部署維運指南。 | `docs/<Module>/CONFIGURATION.md` |
| **維度 7** | 測試與品質指標 | 測試架構、回歸覆蓋率標準與驗收守門矩陣。 | `docs/<Module>/TESTING_GUIDE.md` |

---

## 2. 中觀專題手冊判定準則 (Topic Docs Decision Tree)

凡涉及以下情境之一，**嚴禁**將所有細節塞入單一函式註解或撐爆模組 README，必須建立獨立的 `docs/<Module>/[TOPIC].md` 專題手冊：
1. **多物件協同**：超過 2 個模組或類別協同完成的複雜工作流。
2. **狀態機與生命週期**：包含多階段狀態轉換、超時或回滾邏輯。
3. **資料管線**：包含多階段過濾、轉換、物化或注入的流水線。
4. **通訊與序列化協議**：跨處理程序、跨網路或自定義二進位/文字通訊格式。

---

## 3. 工程妥協與 Design Notes 登記規範

凡包含非直觀實作、Workaround 或為相容性所做的架構妥協：
- **強制標記**：必須在代碼中以 `[DN-<MOD>-XX]` 標記，並使用 `[!CAUTION]` 或 `[!WARNING]` 突顯。
- **知識庫集中登錄**：必須在 `docs/<Module>/DESIGN_NOTES.md` 中詳細記錄其原因、替代方案與未來重構條件。

---

## 4. 三維錨點 1:1 交付驗收原則 (1:1 Delivery Axiom)

在開發計畫結案（Phase 7）審查時，Agent 必須根據 Phase 4 預排的文檔衝擊清單，進行 1:1 核對與驗收，保證代碼與文檔絕對同步。
